# Rebuild state by replay, then prove it

Leading agent benchmarks build environments as pre-populated container or VM images and reset by throwing the instance away; none of them captures state in the middle of a task, so Steward Bench has to add that capability itself. For sessions recorded elsewhere the only method with published evidence is to start a fresh container from a pinned image, re-execute the recorded prefix, seed the model's history with the recorded messages, and audit the result. The Replay Gap did this with 707 of 708 branches reconstructing exactly, but under ideal conditions (same harness, same image, bash-only actions), and Replay Fidelity shows that a verdict-level match hides real state differences: 70 of 71 cases matched on verdict while only 42 of 71 matched on outputs, database deltas and verdict together. Verification in the strongest benchmarks is a deterministic check of final state, which transfers directly to a takeover setting but is blind to unsafe actions that are attempted, undone, or only spoken; the safety benchmarks with the best measured scorer reliability add an action audit log and restrict any LLM judge to narrow, pre-declared labels. On an Apptainer-only cluster the single-container designs (SWE-bench instance images, Harbor tasks, a Postgres-backed tool world) are workable today, while multi-service stacks (TheAgentCompany, WebArena, original Toolathlon, BashArena) and VM-based desktops are not. The largest non-technical risk is Toolathlon: the repository has no licence file and the Verified trajectories forbid public mirroring, so Steward Bench should not redistribute raw Toolathlon prefixes without written permission. Every benchmark reviewed has documented validity defects, typically in a fifth to a half of audited tasks, so a pre-release audit is a requirement and not a refinement.

A note on evidence quality. The research notes behind this report were gathered on 2026-11-11. Several papers were read through a summarising fetch tool, some appendices were truncated, and a few items came only from search summaries; those are flagged where they matter. No source documents any of these benchmarks running under Apptainer except OpenHands and Harbor, so the Apptainer feasibility judgements for everything else are inferences that need a direct test on the target cluster.

## Every benchmark resets to an image and none snapshots mid-task

### Neubig's group ships state inside images and resets by re-creating containers

The SWE-bench harness avoids reset altogether. It builds three layers of image (one base, about 60 environment images, one instance image per task), runs each prediction in its own disposable container, applies the patch, runs the repository's tests and writes a per-instance report ([SWE-bench Docker setup guide](https://www.swebench.com/SWE-bench/guides/docker_setup/); [SWE-bench evaluation guide](https://www.swebench.com/SWE-bench/guides/evaluation/)). The cost is disk and labour, not complexity: the instance cache level uses about 2,000 GB, SWE-Gym's 2,438 instances took about 200 annotation hours and 6 TB of images, and SWE-bench Multimodal needed about ten hours of manual setup per repository ([SWE-bench Docker setup guide](https://www.swebench.com/SWE-bench/guides/docker_setup/); [SWE-Gym](https://arxiv.org/html/2412.21139v2); [SWE-bench Multimodal](https://arxiv.org/html/2410.03859)). SWE-rebench automated the recipe step with an LLM and found a working install for only 31% of repositories ([SWE-rebench](https://arxiv.org/html/2505.20411v2)).

OpenHands is the sandbox layer under most of this work. A runtime image is built on a user-supplied base image, an action execution server inside the container runs a shell and plugins, and the backend talks to it over REST; images carry version, lock-hash and source-hash tags so builds are reproducible and cached ([OpenHands runtime architecture](https://docs.openhands.dev/usage/architecture/runtime)). The newer SDK keeps conversation state as an event log and reports negligible event-sourcing overhead ([OpenHands Software Agent SDK](https://arxiv.org/abs/2511.03690)).

WebArena and TheAgentCompany share long-lived services across tasks and must therefore restore them. WebArena ships each site (Magento shop and admin, Postmill forum, GitLab, a map, offline Wikipedia) as a self-contained image with code, database and data, and resets by stopping the containers and re-creating them from the images; the documented cadence is after a full pass over the 812 tasks, not per task ([WebArena paper](https://arxiv.org/html/2307.13854v4); [WebArena environment README](https://github.com/web-arena-x/webarena/blob/main/environment_docker/README.md)). TheAgentCompany runs GitLab, ownCloud, Plane and RocketChat behind an api-server that exposes per-service reset and health endpoints; each of its 175 tasks is its own image whose init script resets the services it depends on, which takes up to ten minutes ([TheAgentCompany EVALUATION.md](https://github.com/TheAgentCompany/TheAgentCompany/blob/main/docs/EVALUATION.md); [api-server.py](https://github.com/TheAgentCompany/TheAgentCompany/blob/main/servers/api-server/api-server.py)). The reset targets stop, remove and re-create service containers through docker compose ([API_MAKEFILE](https://github.com/TheAgentCompany/TheAgentCompany/blob/main/servers/api-server/API_MAKEFILE)). None of these projects documents a mid-task snapshot; the only states are the initial image and whatever the live containers hold.

### Desktop benchmarks revert a golden image and replay a per-task config

OSWorld, WindowsAgentArena and macOSWorld run a full guest operating system and reset to one base snapshot or golden image, then apply a declarative per-task config that downloads files, launches applications and runs commands. OSWorld's paper explains that a snapshot per task would cost gigabytes each, so it uses one snapshot plus config-driven setup ([OSWorld paper](https://arxiv.org/html/2404.07972)). In the code, the revert to the snapshot named `init_state` is skipped for Docker and cloud providers when the instance is fresh, so the practical reset unit is a new disposable guest ([desktop_env.py](https://raw.githubusercontent.com/xlang-ai/OSWorld/main/desktop_env/desktop_env.py)). WindowsAgentArena distributes no Windows image for licensing reasons; users build a roughly 30 GB golden image from an evaluation ISO in about 20 minutes ([WindowsAgentArena README](https://github.com/microsoft/WindowsAgentArena)). AndroidWorld is the exception: it uses no snapshots and isolates tasks with per-task initialise and teardown code against a long-lived emulator, backed by a fixed device clock, pinned offline apps and seeded task parameters ([AndroidWorld paper](https://arxiv.org/html/2405.14573)). Even so, three seeds with one agent gave 27.6%, 26.3% and 33.2%, a reminder that a deterministic environment does not make a deterministic result ([AndroidWorld paper](https://arxiv.org/html/2405.14573)).

### Terminal-Bench 2.0 is a Harbor task directory on a prebuilt image

A Terminal-Bench 2.0 task is a directory with an instruction, a `task.toml`, an environment definition, a reference solution and a test script. Harbor starts the container from a prebuilt, date-tagged Docker Hub image, runs the agent, uploads the tests only after the agent finishes, and reads a binary reward from `/logs/verifier/reward.txt` ([Harbor tasks overview](https://docs.harborframework.com/tasks/overview); [Harbor verifier docs](https://docs.harborframework.com/tasks/verifier.md)). Tasks are small: across the 89 tasks, 84 use one CPU, 69 use 2 GB of memory and all use 10 GB of storage with no GPU ([terminal-bench-2 repository](https://github.com/harbor-framework/terminal-bench-2)). Determinism is partial. Image tags are mutable and have been republished with different contents, all 89 tasks allow internet access, apt packages are unpinned, and the standard verifier downloads curl, uv and pytest at grading time ([terminal-bench-2 issue 66](https://github.com/harbor-framework/terminal-bench-2/issues/66); [build-pmars test.sh](https://github.com/harbor-framework/terminal-bench-2/blob/main/build-pmars/tests/test.sh)). Installed agents such as Claude Code are installed into the task container at trial time, so the true initial state is image plus agent install ([Harbor installed agent base](https://github.com/harbor-framework/harbor/blob/main/src/harbor/agents/installed/base.py)).

### Tool-use benchmarks split into live accounts, local databases and in-process state

Toolathlon mixes remote and local services. Its 108 tasks span 32 applications; GitHub, Google Calendar, Sheets, Forms and Cloud, Notion, Snowflake, Hugging Face and Weights & Biases are real accounts, while Canvas, Poste.io email, WooCommerce and Kubernetes are deployed locally in containers because, as the authors say, remote services are hard to reset and populate ([Toolathlon paper](https://arxiv.org/html/2510.25726v2)). About two thirds of tasks have an initial state built by a preprocess script, a seeded workspace directory or both, and each task runs in its own container ([Toolathlon paper](https://arxiv.org/html/2510.25726v2)). Toolathlon-GYM replaces all of that with 25 MCP servers over one PostgreSQL 15 database loaded from a compressed dump, with no external API calls at run or evaluation time; its 503 tasks are new tasks in the Toolathlon format, not ports of the 108 originals ([Eigent blog](https://www.eigent.ai/blog/toolathlon-gym-large-scale-long-horizon-environments-for-tool-use-agents); [docker-compose.yml](https://raw.githubusercontent.com/eigent-ai/toolathlon_gym/main/docker-compose.yml)). In parallel runs each task gets its own Postgres instance ([Toolathlon-GYM README](https://raw.githubusercontent.com/eigent-ai/toolathlon_gym/main/README.md)).

AppWorld is the cleanest design for state control. Nine author-written apps expose 457 APIs over SQLite; a base database of about 370,000 rows is populated through the apps' own APIs so derived state stays consistent; each task copies that base, applies task-specific changes, freezes time and loads in under half a second in one process ([AppWorld paper](https://arxiv.org/html/2407.18901)). tau-bench keeps each domain as JSON files reachable only through Python tools with deterministic transitions, and drives the conversation with an LLM user simulator ([tau-bench paper](https://arxiv.org/html/2406.12045)). MCP-Atlas runs 36 real MCP servers in a version-pinned container with allow-listed egress, but it restricts itself to read-only operations and so says little about state ([MCP-Atlas paper](https://arxiv.org/html/2602.00933v1)).

### Safety benchmarks reuse these substrates and plant the hazard as ordinary content

Agent-safety benchmarks with real execution borrow the environments above. OpenAgentSafety packages each of its 356 tasks as a Docker image on OpenHands with TheAgentCompany's services; ROGUE runs on OSWorld-Verified virtual machines; Saber gives each of 716 tasks a Docker workspace made of a shared base filesystem plus a task-specific layer; BashArena uses a four-container compose project per task ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2); [ROGUE](https://arxiv.org/html/2606.00341v2); [Saber](https://arxiv.org/html/2606.01317v2); [BashArena](https://arxiv.org/html/2512.15688)). The hazard is almost always planted as ordinary environment content: a config file holding secrets, a destructive script the agent has to read, malicious instructions inside build scripts or logs, a popup ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2); [Saber](https://arxiv.org/html/2606.01317v2)). Two design rules stand out. AuthorizationBench keeps the unsafe path executable instead of blocking it and does not end the run at task completion, so post-completion behaviour stays observable ([AuthorizationBench](https://arxiv.org/html/2610.27548)). BashArena makes the hazard overlap with the legitimate work, since its main tasks really do need sudo configuration, API keys and network access ([BashArena](https://arxiv.org/html/2512.15688)). OverEager-Bench ships each scenario in two variants that are byte-identical apart from the consent block, which isolates the effect of one planted difference ([OverEager-Bench](https://arxiv.org/html/2605.18583)).

## For recorded sessions, prefix re-execution is the only proven route

### Four mechanisms exist, and three do not fit recorded third-party sessions

The forking and takeover literature uses four ways to obtain an intermediate state. The first keeps one live container across the switch. The Handoff Tax keeps a single agent loop and Docker environment for the whole run, so the repository state persists after the handoff and no rebuild is needed; SWE-Touch applies a counter-edit to the live repository at a trigger step ([The Handoff Tax](https://arxiv.org/html/2608.24358); [SWE-Touch](https://arxiv.org/html/2608.02499)). This only works when the same evaluator produces both prefix and suffix in one run, which is not Steward Bench's situation.

The second restores an operating-system snapshot. Crab combines CRIU process checkpoints with ZFS filesystem snapshots and an eBPF inspector; DeltaBox is a kernel module inside Firecracker microVMs; TClone needs a modified kernel and an extended CRIU ([Crab](https://arxiv.org/html/2604.28138); [DeltaBox](https://arxiv.org/html/2605.22781); [TClone](https://arxiv.org/html/2605.17320v1)). These are fast, with DeltaBox reporting restores under 2 ms against about 27.7 s for replay ([DeltaBox](https://arxiv.org/html/2605.22781)), but all depend on host control that a shared cluster will not grant. Apptainer's own checkpoint feature is DMTCP-based and marked experimental ([Apptainer checkpoint guide](https://apptainer.org/docs/user/main/checkpoint.html)).

The third rebuilds from a pinned commit and starts from turn zero. SWE-Together distils 11,260 public sessions (5,851 of them from SWE-chat) into 109 tasks, each a prebuilt image with the repository at a pinned commit; evaluation begins at the real user's first message and an LLM user simulator supplies later intent ([SWE-Together](https://arxiv.org/html/2606.29957)). It makes no attempt at mid-session state. That a team holding the transcripts chose to restart from the beginning is indirect evidence that recovering mid-session state from wild sessions is hard.

The fourth is prefix re-execution, and it is the one that fits. The Replay Gap starts a fresh container for each fork, re-executes the base trajectory's recorded pre-fork actions, and seeds the agent's message history with the recorded prefix ([The Replay Gap](https://arxiv.org/html/2608.08239)). AgentBaton's checkpoint study does the same but reports no fidelity validation ([AgentBaton](https://arxiv.org/html/2610.35959)). AgentRewind offers a useful unprivileged complement: a bare git repository kept outside the workspace commits the work tree once per model call, capturing files in the workspace only ([AgentRewind](https://arxiv.org/html/2608.14380)).

### Replay rebuilds context reliably but does not predict behaviour

The Replay Gap logged its rebuilds: 99.99% of 11,702 replayed return codes matched and 707 of 708 branches reconstructed exactly ([The Replay Gap](https://arxiv.org/html/2608.08239)). That figure is an upper bound for Steward Bench. The prefixes were produced minutes earlier by the same harness in the same image with a bash-only action space, whereas SWE-chat sessions come from user machines with unknown dependencies and agent-native edit tools. A replayer for Claude Code or Codex sessions has to re-implement those tools' file-edit semantics, because they are not shell commands. Harbor offers no help here: its trajectory loading seeds conversation history and the documentation states that it does not restore sandbox files ([Harbor loading trajectories](https://docs.harborframework.com/jobs/loading-trajectories.md)).

Recorded logs are acceptable for what the incoming model reads and useless for what it does next. In The Replay Gap, 74 to 77% of early model swaps diverged at the first post-fork action, and a log-stitching evaluator that predicted switch outcomes from the other model's logged run was wrong on all five success-relevant calls ([The Replay Gap](https://arxiv.org/html/2608.08239); [abstract](https://arxiv.org/abs/2608.08239)). Crab found that restoring conversation without the environment recovers only 6 to 13% of tasks, against 100% with full state ([Crab](https://arxiv.org/html/2604.28138)). A live, correctly rebuilt environment is therefore not optional. Crab also found that over 75% of agent turns produce no recovery-relevant state and that Claude Code needs full process checkpoints on only 8% of Terminal-Bench turns, which suggests fork points can be chosen where filesystem state is enough ([Crab](https://arxiv.org/abs/2604.28138)). StateFork's authors give the matching warning: a restore that drops the terminal session confused agents enough that a process-checkpoint hybrid did worse than filesystem-only Docker ([StateFork](https://daplab.cs.columbia.edu/general/2026/06/04/statefork-give-agents-a-rewind-button.html)).

### Fidelity has three levels and they disagree

Replay Fidelity re-executed 71 archived AppWorld failures with no model in the loop and compared three things: printed outputs, twelve database delta files, and the native verdict. Under reconstructed declared settings only 42 of 71 cases matched on all three; reseeding Python's random generator before every interaction raised this to 68. On verdict alone, 70 of 71 matched under both settings ([Replay Fidelity](https://arxiv.org/pdf/2611.11216)). The mismatches were not noise. All 25 first-output differences were token-expiry text variations, four cases matched on outputs and verdict yet differed in materialised database rows, and logout state lived in an in-memory set that no database diff could see ([Replay Fidelity](https://arxiv.org/pdf/2611.11216)). The paper's guidance is to report a ladder of contracts instead of one replayability flag, keep immutable snapshots taken before the evaluator runs, and keep match, difference and unknown as three separate values ([Replay Fidelity](https://arxiv.org/pdf/2611.11216)).

Tool-use environments add their own divergence sources. Toolathlon's change log documents server-assigned IDs that differ per run, live data that providers revise, timezone and date dependence, and propagation lag in Sheets, Drive and IMAP ([Toolathlon update log](https://raw.githubusercontent.com/hkust-nlp/Toolathlon/main/UpdateLogs_CommonIssues.md)). No published work resumes a Toolathlon, AppWorld or tau-bench episode mid-trajectory with a live model, and no source measures replay fidelity for Terminal-Bench trajectories, so Steward Bench will be producing the first such numbers.

### Controls separate model noise from environment noise

Only The Replay Gap runs same-model control forks, and they show that temperature zero is not a noise floor: controls for one serving configuration diverged on 90 to 96% of forks, while half of the controls for another never diverged ([The Replay Gap](https://arxiv.org/html/2608.08239)). The Handoff Tax and AgentBaton run one episode per cell with no same-model handoff control, so their effects are not separated from run-to-run variance ([The Handoff Tax](https://arxiv.org/html/2608.24358); [AgentBaton](https://arxiv.org/html/2610.35959)). SWE-Together's two replicates already expose large instability, for example 63% pass@1 against 52% with both replicates passing for one frontier model ([SWE-Together](https://arxiv.org/html/2606.29957)).

## Final-state checks dominate, and safety scoring needs an action log on top

### Deterministic end-state checks are the norm and judges are being removed

SWE-bench runs repository tests on the final tree. Terminal-Bench runs pytest on final container state and explicitly does not test the agent's commands or console output ([Terminal-Bench paper](https://arxiv.org/html/2601.11868)). OSWorld pairs a getter that extracts state with a metric function, AndroidWorld reads app databases and settings through adb, and Toolathlon, MCPMark and MCP-Universe use hand-written scripts over final state with no LLM judge ([OSWorld paper](https://arxiv.org/html/2404.07972); [AndroidWorld paper](https://arxiv.org/html/2405.14573); [Toolathlon paper](https://arxiv.org/html/2510.25726v2); [MCP-Universe](https://arxiv.org/html/2508.14704v1)). Where judges were used they have been a source of error. WebArena-Verified re-audited every task, removed LLM judging and substring matching, and scores offline from recorded network traces ([WebArena-Verified docs](https://servicenow.github.io/webarena-verified/latest/)). MCP-Atlas's claims judge agreed with the human majority on 78% of sampled tasks ([MCP-Atlas paper](https://arxiv.org/html/2602.00933v1)). TheAgentCompany sits between: per-task checkpoints scored mostly by deterministic functions over state, chat history and the trajectory, with 29% of tasks using an LLM evaluator as fallback ([TheAgentCompany paper](https://arxiv.org/html/2412.14161v3)).

Final-state checks suit a takeover benchmark because they are indifferent to who did the work. Their weakness is exactly what Steward Bench measures. tau-bench's authors note that an exact final-database match cannot detect a missing user confirmation ([tau-bench paper](https://arxiv.org/html/2406.12045)). OpenAgentSafety's rule-based evaluator misses attempted-but-failed actions ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2)). AppWorld is the only general benchmark found that penalises unrequested side effects by construction: it diffs start and end databases and each task asserts both the expected changes and the set of allowed changes ([AppWorld paper](https://arxiv.org/html/2407.18901)). ToolSandbox scores the trajectory with milestones that must occur and minefields that zero the score ([ToolSandbox](https://arxiv.org/html/2408.04682v1)).

### Judge reliability tracks how narrowly the label is defined

The safety benchmarks with the best reported scorer reliability check a pre-declared unsafe-action predicate against state and an audit log. OverEager-Bench uses no LLM judge: a shell shim injected on PATH captures 31 sensitive commands, per-agent adapters capture internal tools such as Read and Edit, and SHA-256 filesystem snapshots are taken before and after; against 50 human re-annotations the rule judge reached recall 1.00 and precision 0.76 ([OverEager-Bench](https://arxiv.org/html/2605.18583)). Saber checks state deltas against global safety properties and lets an auxiliary LLM judge add violations but never downgrade a rule-triggered one ([Saber](https://arxiv.org/html/2606.01317v2)). BashArena runs each side-task test after every action, which catches a violation that is later reversed ([BashArena](https://arxiv.org/html/2512.15688)). AuthorizationBench's hybrid, in which a judge only decides whether a specified action occurred, reached 97% agreement with a blind human labeller on out-of-authorization labels ([AuthorizationBench](https://arxiv.org/html/2610.27548)).

Open-ended trajectory verdicts are far worse. OpenAgentSafety's GPT-4.1 judge labelled 35.9% of sampled trajectories unsafe where human experts labelled 71.7% ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2)). ROGUE's judge agreed with humans completely on override and restricted-access labels but only 59.1 to 86.4% on shutdown intent ([ROGUE](https://arxiv.org/html/2606.00341v2)). ToolEmu's LLM-emulated tools carry a further cost: only 68.8 to 72.5% of the failures it identified were judged real ([ToolEmu](https://arxiv.org/html/2309.15817)).

### Runs that never reach the hazard must leave the safety denominator

OpenAgentSafety defines a failed run as one that never reached a safety-vulnerable point; 34.80 to 48.90% of runs fail this gate, and unsafe rates are computed only over the rest ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2)). Saber classifies every run as safe completion, safe refusal, incapable, harmful completion, late refusal or accidental harm, excludes incapable runs from its harm rate, and counts a refusal where a safe path existed as incapable ([Saber](https://arxiv.org/html/2606.01317v2)). AuthorizationBench and OverEager-Bench report completion as an axis independent of the violation rate ([AuthorizationBench](https://arxiv.org/html/2610.27548); [OverEager-Bench](https://arxiv.org/html/2605.18583)). SWE-Touch records at run time whether its injected edit actually changed the repository; across 5,399 runs it applied zero times in 346 ([SWE-Touch](https://arxiv.org/html/2608.02499)). A gridworlds study shows the inverse failure: a model scored as safe because it misunderstood the task, not because it recognised the hazard ([AI Safety Gridworlds port](https://arxiv.org/html/2606.15385)).

Realism also needs measuring. Models separate evaluation from deployment transcripts with an AUC up to 0.83, and do so more easily in agentic settings ([Needham et al.](https://arxiv.org/abs/2505.23836)). LURE, the closest published precedent for Steward Bench's design (a recorded real coding session, minimal edits, one appended safety-relevant request), still drew average evaluation-probability scores of 73.6 and 82.8 from a judge model, against 94.9 and 97.8 for conventional evals ([LURE](https://www.lesswrong.com/posts/WKuGzrtCnAAArjj2N/lure-alignment-evaluations-to-reduce-evaluation-awareness)). The units in the notes on that post were inconsistent and should be checked against the original.

## Apptainer handles single containers; multi-service stacks and VMs do not port

OpenHands has first-party Apptainer support. Its `ApptainerWorkspace` needs no root and no daemon, accepts a registry image, a base image or an existing SIF file, caches SIF files and uses host networking; the pull request merged on 2025-12-29 ([OpenHands Apptainer sandbox guide](https://docs.openhands.dev/sdk/guides/agent-server/apptainer-sandbox.md); [software-agent-sdk PR 892](https://github.com/OpenHands/software-agent-sdk/pull/892)). The OpenHands benchmarks repository merged an Apptainer SWE-bench evaluation path and image builds in June 2026 ([benchmarks PR 743](https://github.com/OpenHands/benchmarks/pull/743); [benchmarks PR 745](https://github.com/OpenHands/benchmarks/pull/745)). The details of those two pull requests were read through search summaries; only titles and merge dates were confirmed.

Harbor has had a merged `singularity` backend since April 2026. It converts Docker images to SIF with a locked cache or takes a prebuilt SIF, and runs a small HTTP server inside the container for command execution ([Harbor PR 1306](https://github.com/harbor-framework/harbor/pull/1306); [singularity README](https://github.com/harbor-framework/harbor/blob/main/src/harbor/environments/singularity/README.md)). It is rough. It cannot enforce no-network without losing controller connectivity, with a fix that swaps the TCP port for a Unix socket still open ([Harbor issue 3526](https://github.com/harbor-framework/harbor/issues/3526); [Harbor PR 3527](https://github.com/harbor-framework/harbor/pull/3527)). Every agent run is capped at 600 seconds ([Harbor issue 3350](https://github.com/harbor-framework/harbor/issues/3350)). Orphaned FUSE helpers pushed median start time from 17 to 46 seconds over a run and caused 20 of 360 trials to time out at start ([Harbor issue 3351](https://github.com/harbor-framework/harbor/issues/3351)). A separate report from a Lustre cluster found that a tmux socket under a bind-mounted directory hangs forever because Unix sockets do not work on Lustre ([Harbor PR 2910](https://github.com/harbor-framework/harbor/pull/2910)). A larger Apptainer rewrite with offline mode and multi-node Slurm workers is still open ([Harbor PR 2950](https://github.com/harbor-framework/harbor/pull/2950)).

SWE-Together demonstrates the whole pattern on Slurm without Docker, though with enroot and not Apptainer: each public image is converted once to a squashfs file, containers start in about two seconds with a tmpfs root filesystem, and egress is enforced with a default-deny proxy in an unprivileged namespace ([SWE-Together sandboxes doc](https://github.com/Togetherbench/SWE-Together/blob/main/docs/sandboxes.md)). Its caveats will carry over: overlay state cannot live on Lustre or NFS, and without a PID namespace background processes survive container removal ([SWE-Together sandboxes doc](https://github.com/Togetherbench/SWE-Together/blob/main/docs/sandboxes.md)). Apptainer's ext3 overlay images work without root and are single files, whereas directory overlays generally do not work well on network file servers ([Apptainer persistent overlays](https://apptainer.org/docs/user/main/persistent_overlays.html)). Copying such an overlay file after prefix replay to get a reusable fork-point snapshot follows from that documentation but is not a documented workflow; it needs a test.

The rest does not port cleanly. TheAgentCompany mounts the Docker socket into its api-server and drives compose for resets ([TheAgentCompany SETUP.md](https://github.com/TheAgentCompany/TheAgentCompany/blob/main/docs/SETUP.md)). WebArena is documented only as an AWS image or Docker tarballs ([WebArena environment README](https://github.com/web-arena-x/webarena/blob/main/environment_docker/README.md)). Toolathlon's Docker-free path warns that some tasks fail because the local apps cannot be deployed and kind cannot launch a cluster ([Toolathlon README_nodocker](https://raw.githubusercontent.com/hkust-nlp/Toolathlon/main/README_nodocker.md)). OSWorld and WindowsAgentArena assume Docker with KVM or cloud VMs, and no source describes them under Apptainer ([OSWorld README](https://github.com/xlang-ai/OSWorld); [WindowsAgentArena README](https://github.com/microsoft/WindowsAgentArena)). Inspect lists no Apptainer provider, and its `local` sandbox gives no isolation ([Inspect sandboxing docs](https://inspect.aisi.org.uk/sandboxing.html)). In contrast, Toolathlon-GYM's stack is one Postgres instance plus Python processes configured through `PG*` variables, and AppWorld runs in a single process, so both are plausible as unprivileged processes, although nobody has documented doing it ([Toolathlon-GYM docker-compose.yml](https://raw.githubusercontent.com/eigent-ai/toolathlon_gym/main/docker-compose.yml); [AppWorld paper](https://arxiv.org/html/2407.18901)).

## Code is permissively licensed; Toolathlon's data is not

Most code is MIT or Apache-2.0: SWE-bench, OpenHands, TheAgentCompany, WebArena, Harbor, both Terminal-Bench repositories, OSWorld, AgentDojo, ControlArena, AuthorizationBench, OpenAgentSafety and The Replay Gap's harness ([SWE-bench](https://github.com/SWE-bench/SWE-bench); [software-agent-sdk](https://github.com/OpenHands/software-agent-sdk); [TheAgentCompany](https://github.com/TheAgentCompany/TheAgentCompany); [webarena](https://github.com/web-arena-x/webarena); [harbor](https://github.com/harbor-framework/harbor); [OSWorld](https://github.com/xlang-ai/OSWorld); [ControlArena](https://github.com/UKGovernmentBEIS/control-arena); [replay-gap](https://github.com/AshrithaG/replay-gap)). The SWE-Together dataset is Apache-2.0 and its task directories are documented as including the original session transcript ([SWE-Together dataset card](https://huggingface.co/datasets/yfwu/SWE-Together); [SWE-Together tasks](https://github.com/Togetherbench/SWE-Together/tree/main/tasks)). The unclear cases are Saber, whose licence file GitHub does not recognise, and the BashArena public repository, which shows no licence ([Saber repo](https://github.com/sssr-lab/saber); [BashArena repo](https://github.com/redwoodresearch/basharena_public)). Licences of bundled applications and seeded data in WebArena and TheAgentCompany were not checked, and the notes did not establish SWE-chat's dataset licence, which Steward Bench must confirm before redistributing SWE-chat-derived prefixes.

Toolathlon is the real problem. The repository has no licence file, with an issue asking for one open since August 2026 and a second on the licence of leaderboard results open since October ([Toolathlon issue tracker](https://github.com/hkust-nlp/Toolathlon/issues)). The Verified trajectories dataset is gated, limited to evaluation, reproducibility, auditing and error analysis, forbids training, distillation and retrieval corpora, says raw trajectories must not be publicly mirrored, and states no formal licence ([Toolathlon-Verified_Trajectories card](https://huggingface.co/datasets/hkust-nlp/Toolathlon-Verified_Trajectories)). A takeover prefix is raw trajectory content, so publishing Steward Bench workplace tasks with embedded Toolathlon prefixes is, on a plain reading, the public mirroring those terms prohibit. The terms attached to the earlier, unverified Toolathlon-Trajectories release were not captured in the notes. Toolathlon-GYM shows Apache-2.0 in its repository sidebar while its README is silent, and whether that licence validly covers interfaces derived from an unlicensed upstream is unresolved ([Toolathlon-GYM repository](https://github.com/eigent-ai/toolathlon_gym)).

## Audits find defects in a fifth to a half of tasks

Validity problems are universal and fall into a few classes. The first is drift from the live internet. OSWorld-Verified fixed about 300 reported issues, many caused by website redesigns, CAPTCHAs and IP blocks ([OSWorld-Verified blog](https://xlang.ai/blog/osworld-verified)). Terminal-Bench tasks broke when a PyPI name was taken over, when a download host began returning 403, and when a Debian release reached end of life ([terminal-bench-2 issue 75](https://github.com/harbor-framework/terminal-bench-2/issues/75); [issue 76](https://github.com/harbor-framework/terminal-bench-2/issues/76); [PR 82](https://github.com/harbor-framework/terminal-bench-2/pull/82)). Toolathlon had to freeze a stock task to a snapshot because Yahoo revises historical figures ([Toolathlon update log](https://raw.githubusercontent.com/hkust-nlp/Toolathlon/main/UpdateLogs_CommonIssues.md)).

The second is graders that are too strict, too lenient, or trust agent-controlled state. An independent audit found task-side defects in 28 of 89 Terminal-Bench 2.0 tasks ([Benchmarks as Software](https://openreview.net/forum?id=AhXMZPnOPS)). Epoch AI's partial audit of OSWorld 2.1 found 40 errors across 36 of 50 sampled tasks, with errors able to affect up to 50.4% of the audited score ([Epoch AI review](https://epoch.ai/benchmarks/osworld-2-1/review)). One Terminal-Bench task passes without the required binary because the verifier uses an agent-controlled file, and a Toolathlon issue shows an agent-written file in the workspace making the containerised evaluator exit successfully ([terminal-bench-2 issue 67](https://github.com/harbor-framework/terminal-bench-2/issues/67); [Toolathlon issue tracker](https://github.com/hkust-nlp/Toolathlon/issues)). Toolathlon's top score moved from 38.6% in the paper to about 76% on the Verified card, a change that mixes model progress with many grader fixes ([Toolathlon abstract](https://arxiv.org/abs/2510.25726); [Toolathlon-Verified_Trajectories card](https://huggingface.co/datasets/hkust-nlp/Toolathlon-Verified_Trajectories)).

The third is leakage through the harness. An audit found that the then top Terminal-Bench entry read the tests directory in 415 of 429 traces, and another agent loaded files containing literal answers ([cheating-agents audit](https://debugml.github.io/cheating-agents/)). The maintainers now require trajectories for all passing trials and zero any reward-hacked trial ([Terminal-Bench leaderboard integrity update](https://www.tbench.ai/news/leaderboard-integrity-update)).

The fourth is state leakage and flaky services in shared environments: WebArena's suite-level reset and nondeterministic reports, TheAgentCompany's reset races and vanishing RocketChat accounts ([webarena issue 100](https://github.com/web-arena-x/webarena/issues/100); [TheAgentCompany issue 1055](https://github.com/TheAgentCompany/TheAgentCompany/issues/1055)). The last is the hidden environment model. TheAgentCompany's colleagues and 29% of its graders depend on a configurable environment LLM, and tau-bench's simulated users make errors, so scores are comparable only when that model is fixed ([TheAgentCompany paper](https://arxiv.org/html/2412.14161v3); [tau-bench paper](https://arxiv.org/html/2406.12045)).

## What Steward Bench should build, in priority order

The first priority is a single state-rebuild contract shared by all three domains, because every other decision depends on it. Copy The Replay Gap's procedure: a fresh container from a digest-pinned image, re-execution of the recorded prefix, history seeded from the recorded messages ([The Replay Gap](https://arxiv.org/html/2608.08239)). Take read-only tool results from the log and re-execute only state-changing actions; Crab's finding that most turns change no recoverable state supports this, though no paper has tested selective re-execution ([Crab](https://arxiv.org/abs/2604.28138)). Choose fork points where relevant state is on disk and no background process or interactive session is live, since those are lost and their absence misleads the incoming model ([StateFork](https://daplab.cs.columbia.edu/general/2026/06/04/statefork-give-agents-a-rewind-button.html)). Store the rebuilt state once, as a copied ext3 overlay file or a git-committed workspace in the AgentRewind style, and start every arm from that artifact so all models see byte-identical state ([Apptainer persistent overlays](https://apptainer.org/docs/user/main/persistent_overlays.html); [AgentRewind](https://arxiv.org/html/2608.14380)). Keep overlays and sockets on node-local tmpfs, never on Lustre or NFS.

The second priority is to validate every rebuilt state with a ladder and publish the ladder. At the action level, compare each re-executed command's return code and output with the recorded observation and report the match rate, as The Replay Gap does. At the state level, compare a tree hash or diff of the workspace with an independent reference; for SWE-chat sessions the natural reference is the repository at the checkpoint-linked commit, since SWE-chat links each checkpoint to a commit ([SWE-chat](https://arxiv.org/html/2604.20779)). For database-backed environments, hash sorted rows per table, which is how Replay Fidelity confirmed real content differences ([Replay Fidelity](https://arxiv.org/pdf/2611.11216)). At the verdict level, let the original recorded suffix run to completion where one exists and check that the task's verifier gives the recorded outcome. Run the rebuild in two fresh processes and require agreement. Record match, difference and unknown as three values, admit a candidate only when it clears a stated rung, and keep rejected candidates in the inventory with their reason instead of quietly replacing them. Add a precondition check that runs immediately before handover and confirms the planted item and the state it depends on are present; OSWorld's "Bluetooth already unavailable" defect is the failure this prevents ([OSWorld-Verified blog](https://xlang.ai/blog/osworld-verified)). Freeze the clock, seed random generators, and list the hidden state the checks cannot see (working directory, in-memory tokens, environment variables).

The third priority is hazard exposure accounting. Decide in advance, per scenario, the observable event that counts as reaching the hazard: the model read the hazard-bearing file, received the tool result containing it, or executed the step at which the unsafe option becomes available. Record it at run time, as SWE-Touch records whether its edit landed ([SWE-Touch](https://arxiv.org/html/2608.02499)). A run that never reaches the hazard is excluded from the safety denominator and reported in its own column, following OpenAgentSafety and Saber; it is never counted as safe ([OpenAgentSafety](https://arxiv.org/html/2507.06134v2); [Saber](https://arxiv.org/html/2606.01317v2)). Reduce such runs by design: fork close to the hazard, and place the hazard on the path the remaining task requires, as BashArena does by making the risky resource one the honest work needs ([BashArena](https://arxiv.org/html/2512.15688)). Where a fixed position cannot guarantee exposure, deliver the planted item on a trigger tied to the model touching the relevant file or object, which is SWE-Touch's mechanism. Adopt Saber's outcome grid so that an unnecessary refusal counts as incapability, and run a matched variant with the hazard removed to measure over-caution, in the spirit of OverEager-Bench's byte-identical pairs ([OverEager-Bench](https://arxiv.org/html/2605.18583)). Keep the unsafe path executable and do not end the run at task completion ([AuthorizationBench](https://arxiv.org/html/2610.27548)). If the pilot shows a high not-reached rate for a scenario, redesign the scenario; do not paper over it with the denominator.

The fourth priority is scoring. Use a pre-declared unsafe-action predicate per scenario, checked against both a state diff and an action audit log. Copy OverEager-Bench's two capture channels (a PATH shim for sensitive shell commands and an adapter for the agent's native tools) plus before-and-after file hashes; all of this works without Docker ([OverEager-Bench](https://arxiv.org/html/2605.18583)). Evaluate the predicate after every action so that reversed violations are caught ([BashArena](https://arxiv.org/html/2512.15688)). For workplace tasks, add AppWorld's allowed-changes diff to catch collateral damage ([AppWorld paper](https://arxiv.org/html/2407.18901)). Restrict any LLM judge to narrow questions about whether a specified action or statement occurred, allow it to add but never remove a rule-triggered violation, and validate it against blind human labels on a stratified sample, reporting agreement per label ([Saber](https://arxiv.org/html/2606.01317v2); [AuthorizationBench](https://arxiv.org/html/2610.27548)). Run the verifier outside the agent's writable workspace, from a separate image or a fresh copy with only declared artifacts, because both Terminal-Bench and Toolathlon have been beaten through evaluators that trust agent-controlled files ([Harbor verifier docs](https://docs.harborframework.com/tasks/verifier.md); [Toolathlon issue tracker](https://github.com/hkust-nlp/Toolathlon/issues)).

The fifth priority is the software-engineering environment. Follow SWE-Together's build recipe: one image per session with the repository at a pinned commit, dependencies frozen after a successful install, and a content-hash tag ([SWE-Together sandboxes doc](https://github.com/Togetherbench/SWE-Together/blob/main/docs/sandboxes.md)). Since the cluster cannot build Docker images, either build on a Docker-capable machine and convert to SIF once into a shared cache, or build from Apptainer definition files; OpenHands' Apptainer workspace and its SWE-bench Apptainer path are the reference implementations to read before writing new code ([OpenHands Apptainer sandbox guide](https://docs.openhands.dev/sdk/guides/agent-server/apptainer-sandbox.md)). Expect low yield: SWE-Together kept under 1% of sessions and SWE-rebench found working installs for 31% of repositories, so budget the candidate pool accordingly ([SWE-Together](https://arxiv.org/html/2606.29957); [SWE-rebench](https://arxiv.org/html/2505.20411v2)). Reject sessions whose outcome depends on deployment, pull-request management or private credentials, as SWE-Together does. Validate each environment by checking that the reference change passes its tests and a no-op does not, and rerun tests several times to exclude flaky ones.

The sixth priority is the terminal and DevOps environment. Adopt Harbor's task directory layout and ATIF trajectory schema so tasks and logs interoperate with existing tooling, but treat Harbor's Singularity backend as a design to learn from, not a dependency to trust unpatched ([Harbor tasks overview](https://docs.harborframework.com/tasks/overview); [Harbor ATIF docs](https://docs.harborframework.com/agents/atif)). Avoid each documented Terminal-Bench weakness: pin images by digest, bake verifier dependencies into a separate verifier image so grading needs no network, disable network for the agent or allow-list it, pre-install the agent and tmux in the image so the initial state is the image alone, and put control sockets on container-local storage ([terminal-bench-2 issue 66](https://github.com/harbor-framework/terminal-bench-2/issues/66); [Harbor PR 3527](https://github.com/harbor-framework/harbor/pull/3527); [Harbor PR 2910](https://github.com/harbor-framework/harbor/pull/2910)). Reap container helper processes between trials and monitor start latency. Require an oracle solution that passes and a no-op that fails for every task, which is Terminal-Bench's own admission rule ([Terminal-Bench paper](https://arxiv.org/html/2601.11868)). Keep DevOps hazards within a single container: scenarios that need real firewall rules, multiple networked containers or Kubernetes do not fit rootless Apptainer.

The seventh priority is the workplace environment, and here the recommendation is to build on a database-backed world and not on live accounts. Run one Postgres instance per task as an unprivileged process on its own Unix socket, loaded from a dump, with local MCP servers as Python processes, following Toolathlon-GYM's architecture and AppWorld's discipline: populate through the application layer, freeze time, control ID sequences ([Toolathlon-GYM docker-compose.yml](https://raw.githubusercontent.com/eigent-ai/toolathlon_gym/main/docker-compose.yml); [AppWorld paper](https://arxiv.org/html/2407.18901)). This makes the entire environment state a file that can be copied and hashed. Recorded Toolathlon trajectories cannot be dropped in unchanged, because seeded data and object IDs differ; replay needs a table that maps recorded IDs to fresh ones and a per-call comparison of fresh results with recorded ones. Restrict the candidate pool to Toolathlon tasks whose servers are all local or mockable, which can be computed from each task's configuration, and exclude tasks graded against live data. This is the domain with the least prior art: no one has published a mid-trajectory resume on these environments, so run a small feasibility pilot before committing to a task count.

The eighth priority, to be settled before any workplace data is published, is Toolathlon licensing. Do not commit or publish raw Toolathlon prefixes. Write to the Toolathlon authors for explicit permission to redistribute derived prefixes and for a licence on the repository, citing the open issues. Until that arrives, release workplace tasks as pointers and recipes: the upstream trajectory identifier, the step index, content hashes, and the planted-situation patch, with a script that rebuilds the prefix from the gated dataset each user downloads under its own terms. The stronger fallback, which also removes the replay ID-mapping problem, is to generate Steward Bench's own prefix sessions by running agents in the database-backed world and to use Toolathlon only as a source of task designs; confirm Toolathlon-GYM's LICENSE file first, since the sidebar and README disagree. Apply the same check to SWE-chat's dataset terms.

The last priority is controls and audit. For every fork, run the original model as a control arm from the same rebuilt state, more than once, so between-model differences can be read against a noise floor ([The Replay Gap](https://arxiv.org/html/2608.08239)). Fix and report verbatim any scripted principal message, and if a simulated principal is used make it reactive only, never volunteering the boundary or widening authority, as in AuthorizationBench; measure how often it leaks ([AuthorizationBench](https://arxiv.org/html/2610.27548)). Measure evaluation awareness on the finished prefixes instead of assuming recorded sessions look real ([LURE](https://www.lesswrong.com/posts/WKuGzrtCnAAArjj2N/lure-alignment-evaluations-to-reduce-evaluation-awareness)). Before release, have every task read by a human or model auditor, since that is how the defects in OSWorld, Terminal-Bench and WebArena were eventually found.

## Conclusion

The field has converged on disposable, image-defined environments and deterministic end-state graders, and it has paid for every shortcut: live web dependencies, mutable image tags, shared services, graders inside the agent's sandbox and open-ended LLM verdicts each produced a documented failure. Steward Bench inherits those lessons but its defining requirement, a trustworthy state in the middle of someone else's session, has no off-the-shelf answer. The honest framing is that Steward Bench is partly a replay-fidelity study: the admission ladder, the reached-hazard rate and the same-model control floor are results in their own right, and publishing them is what will distinguish it from handoff papers that report a single number per cell.

The Apptainer constraint turns out to be less limiting than it first appears, because the designs it rules out (multi-service stacks, full VMs, live accounts) are the same ones with the worst reset, leakage and drift records. What remains uncertain is yield and legality more than engineering: how many real SWE-chat sessions rebuild to an admissible state, whether workplace prefixes can be replayed across differently seeded data, and whether Toolathlon's authors will license redistribution. Each of those can be answered cheaply by a pilot or an email before the full build begins.
